# Pigmento — Plan

> **Pigmento** — *Paint simply. Create boldly.*
> A friendly raster editor for Windows 11 with the classic Paint layout and room to grow into layers, custom shapes and custom brushes.

This file is the source of truth for scope and progress. Each milestone has a checklist; tick items as they land (one commit per sub-step) so work can resume from here after a context reset.

## 1. Stack decision

| Concern | Choice | Why |
|---|---|---|
| Language | TypeScript 6.0 (strict) | Required. 6.0 rather than 7.x because `typescript-eslint` supports `<6.1`. |
| Desktop shell | Electron 45 | Needs only Node.js on Windows (no Rust/C++ toolchain). Native dialogs, clipboard, jump lists, title-bar overlay with Snap Layouts. |
| Build | electron-vite 6 + Vite 8 | One config builds main, preload and renderer, with HMR in dev. |
| UI | React 19 + Zustand 5 | React for the chrome only. Zustand mirrors engine state for React. |
| Engine | Plain TypeScript, no React | Unit-testable in Node. React talks to it through `Engine`'s typed API and events. |
| Rendering | Canvas 2D + Web Workers | CPU tiled surfaces hold the pixel data, GPU canvases mirror them for display, and workers decode, encode and flood-fill. The renderer interface can later be swapped for WebGL. |
| Validation | Zod 4 | Settings now; shape and brush packs later. |
| Icons | Lucide (ISC) + a few hand-drawn SVGs | Consistent 2px stroke icons, open license. |
| Font | Inter Variable via `@fontsource-variable/inter` (OFL-1.1) | Bundled, readable, no network. |
| GIF encode | `gifenc` (MIT) | Small, dependency-free quantizer and encoder. BMP is a hand-written encoder. |
| Tests | Vitest 5 (unit), Playwright 1.64 `_electron` (e2e) | As specified. |
| Packaging | electron-builder 26 (NSIS + portable) | As specified (Milestone 4). |
| Icons build | `@resvg/resvg-js` (dev only) | Rasterises the SVG logo to PNG/ICO with prebuilt binaries, no native toolchain. |

Security baseline: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, a typed preload bridge, a strict CSP (meta tag, production has no `unsafe-*`), a custom `app://` protocol in production instead of `file://`, blocked navigation and `window.open`, permission requests denied except `local-fonts` and clipboard-write, and all non-local network requests cancelled.

## 3. Core architecture

### 3.1 Engine/UI boundary
- The UI calls only `Engine` methods (`engine.setTool`, `engine.undo()`, `engine.image.rotate(90)`, …) and subscribes with `engine.on(event, fn)`.
- The engine emits typed events: `doc`, `history`, `view`, `selection`, `tool`, `live`, `cursor`, `colors`, `dirty`.
- Host services (files, clipboard, dialogs) live in the UI layer and call the preload bridge `window.pigmento`. The engine never touches IPC.

### 3.2 Document model
`Document { width, height, dpi, paper: RGBA | null, layers: Layer[], activeLayerId, selection }`
- `paper` is the canvas background colour, composited under every layer and exported unless transparent. The eraser, Delete and moving a selection reveal the paper (see Assumptions).
- `Layer` is the base type; Milestone 1 ships `RasterLayer` (`Surface` + opacity, blend, visible, locked). The model already has a layer list with blend and opacity, so Milestone 2 adds vector and group layers without changes to the core.
- **Live objects** (a shape being edited, a text box, a floating selection) belong to the engine rather than the document. They render above the active layer and rasterise into it on commit as a single history command.

### 3.3 Pixels: tiled surfaces
- `Surface` holds straight RGBA8 pixels in 256×256 tiles of `Uint8ClampedArray`. A `null` tile is fully transparent, so empty areas cost nothing.
- Edits go through `beginEdit()/endEdit()`. The first write to a tile captures its previous array (copy-on-write) and `endEdit()` returns a **TileDelta** containing only the tiles that actually changed.
- Each layer also has a doc-sized GPU **mirror canvas** that is only ever written with `putImageData`, never read back. This avoids GPU readback stalls.

### 3.4 History
- Command pattern: `{ label, undo(), redo(), bytes }`. A command is pushed after its action has already been applied.
- `TileDeltaCommand` undoes and redoes by swapping tile arrays, so one stored copy serves both directions. Self-inverse operations (flip, rotate 90/180/270) store no pixels. Size changes (crop, resize, canvas size) store the replaced surfaces.
- A memory budget (default 1 GB) evicts the oldest commands. The History panel lists the states and lets you click one to jump to it.

### 3.5 Rendering
- **Compositor:** a doc-sized composite canvas updated only inside dirty rectangles: clear, then each visible layer mirror with its blend and opacity, with the live object inserted after the active layer.
- **View:** a screen-sized canvas showing the workspace background, the document shadow, a checkerboard (fixed screen size) and the composite under the view transform. Smoothing is off at 200% and above (crisp pixels). The pixel grid appears at 800% and above.
- **Overlay:** a separate canvas for marching ants, handles, the brush cursor, previews and grid lines. It never touches pixel data.
- High-DPI: canvas backing stores use `devicePixelRatio` and re-size when it changes (per-monitor DPI).

### 3.6 Tools (plugin interface)
```ts
interface Tool {
  id; labelKey; icon; shortcut?; group; order;   // placement in ribbon is data-driven
  cursor(ctx): CursorSpec;
  getOptionsSchema(): OptionSpec[];               // options bar renders from this
  onActivate?/onDeactivate?;
  onPointerDown/Move/Up(e: ToolPointerEvent, ctx: ToolContext);
  onKeyDown?(e, ctx): boolean;
  renderOverlay?(ov: OverlayContext, ctx);
}
```
Tools live in `engine/tools/builtin/*.ts` and register themselves. `import.meta.glob` loads every file, so adding a tool means adding one file.

### 3.7 Input
Pointer Events with `getCoalescedEvents()`, pressure and tilt, and the pen eraser end (`buttons & 32`) temporarily switching to the eraser. Touch is ignored while a pen is down (palm rejection). Two-finger touch pinches to zoom and pans. Middle mouse or Space+drag pans, Ctrl+wheel zooms at the cursor, Shift+wheel scrolls horizontally.

### 3.8 Main process and storage
- User data lives in `%APPDATA%\Pigmento\` (overridable with `PIGMENTO_USER_DATA` for tests): `settings.json`, `recent.json`, and later `library/`, `autosave/`.
- Every write is atomic: write `*.tmp`, fsync, then rename, with a retry on Windows `EPERM`/`EBUSY`.
- A single-instance lock means "Open with" or the jump list sends the file to the running app, which opens a new window unless the current one is an untouched blank document.
- Native dialogs, clipboard (`nativeImage`), print (a hidden window holding the flattened PNG, then `webContents.print`), and wallpaper (PNG under AppData, then PowerShell P/Invoke `SystemParametersInfo`).

### 3.9 Registries
`ToolRegistry` (Milestone 1), then `ShapeRegistry` (Milestone 2), `BrushRegistry` and `FilterRegistry` (Milestone 3). All of them use Zod schemas, and built-in and user items go through the same registry and schema.

## 4. Assumptions and decisions
1. **Name and brand:** Pigmento. Primary accent Ultramarine `#4B4BE0`, secondary accent Cadmium `#FF8A3D`. Native project file `.pigm`, brush pack `.pigmbrush`.
2. **Paper background:** each document has a paper colour (default white). Classic Paint paints the secondary colour when you erase or move a selection. Pigmento makes those pixels transparent on the layer, which reveals the paper. A beginner sees the same result, and it works cleanly with layers. Opened images get white paper if they are fully opaque, otherwise transparent paper, so alpha is preserved when saving.
3. **Text:** text boxes grow to fit (point text). New lines come from Enter, with no automatic wrapping, so the on-canvas preview and the rasterised result match exactly.
4. **Single document per window.** File > New/Open replaces the document after an unsaved-changes prompt. "Open with" while the app is running opens a new window.
5. **Native message box** for "Save changes?" prompts (Save / Don't save / Cancel), because it is the most Windows-native.
6. **Colours carry alpha.** Primary and secondary colours may be semi-transparent, set in Edit colours.
7. **Ribbon tabs appear when they have content.** Milestone 1 ships Home, Image and View. Shapes, Brushes and Effects arrive with their milestones, per the "nothing unbuilt in the UI" rule.
8. **Saved palette files** (.json/.gpl/.ase import and export) land in Milestone 2. Milestone 1 has the built-in palette, recent colours and "Add to custom colours", persisted in settings.
9. **SVG export** lands in Milestone 2, when vector objects can export as real paths. Raster-only SVG adds little.
10. **Wallpaper:** the implementation is tested with a read-only `SystemParametersInfo` query, so development and tests never change the real desktop.
11. **Help and About** are allowed earlier than Milestone 4 if they are complete. The full shortcut editor stays in Milestone 4, but every shortcut already goes through the action registry.
12. **Eraser** makes layer pixels transparent (reveals the paper). More eraser variants arrive in Milestone 3.

### Milestone 5 — Animation mode (requested after 1.0)
Keyframe animation of pieces cut from a selection (move, rotate, scale, stretch, skew, fade, curved motion paths, movable pivot), frame-by-frame drawing with onion skin, and export to animated GIF and MP4. Split into four stops; each ends with a working app, `npm run check` green and a report, then waits for "continue". Each item is ticked in the same commit as its work.

Words used in the UI: the **timeline** (fps 1–60, default 12; length 1–2000 frames, default 24; loop, once or ping-pong), a **piece** (pixels lifted from a selection on a pixel layer, drawn just above that layer's pixels and inside the layer), a **keyframe** (position, scale X/Y, rotation, skew, opacity, easing to the next keyframe, optional motion-path handles; held before the first and after the last; rotation isn't wrapped), the **pivot** (what a piece turns and scales around; moving it never moves the piece), and a **cel** (one drawing of a frame-by-frame layer, shown from its start frame until the next cel).

Decisions: pieces come only from pixel layers; shape layers and text aren't frame-by-frame; pieces are cut-outs (animated, not repainted); animation is Full mode only; MP4 has no sound.

### Milestone 6 — Pieces in 3D, version 1.2.0 (requested after 1.1.1)
Pieces become sheets of paper in 3D space: tilt, turn and push them back under one camera, hinge them edge to edge into boxes and other shapes that move as one, keep them outside the canvas and repeat them for scrolling backgrounds, and paint on them where they stand. Split into four stops; each ends with a working app, `npm run check` green and a report, then waits for "continue". Each item is ticked in the same commit as its work.

Words used in the UI: the **camera** (one per picture: a **vanishing point**, at the canvas centre to start with, and a **perspective** strength from flat to strong; it can **pan** and **push in or out**), a piece's **transform** (the 1.1 keyframe values, with rotation now called **spin**, plus **depth** (further away), **tilt** (top edge back or forward) and **turn** (round the upright, like a door)), **repeat** (a piece tiles across, down or both) and **scroll** (where the tiles start, keyframed), a **hinge** (one piece's edge fixed to another piece's edge, with a **fold** angle), **attach** (a piece follows another without a hinge, flat or in 3D), a **group** (pieces linked by hinges or attaching, with its own transform about a pivot at its centre), a piece's **back** (mirrored, like paper, or hidden) and **shading** (a face darkens as it turns away from the light).

Decisions (agreed with the user):
- The transform mask is the piece's transform. It's non-destructive: it never changes the piece's pixels, Reset lays the piece flat again, and Flatten into layer paints it into its layer as one undo step. Layers don't get masks, because they stop at the canvas edge and scrolling needs pixels beyond it.
- Pieces still belong to pixel layers. Besides a selection, a piece can come from a whole layer, a placed image file or a paste; it can be bigger than the canvas and sit anywhere, partly or wholly outside it.
- Painting on pieces replaces 1.1's "pieces are cut-outs" rule: the brush-engine tools (Brush, Pencil, Eraser, Smudge, Blur, Sharpen, Clone Stamp, Dodge/Burn) and Fill paint the selected piece's own pixels through its transform. Other tools work on layers only, and painting on a piece ignores the selection.
- Links are hinges with a fold angle plus groups. Links stay on one layer, so a layer's pieces are drawn together.
- Pseudo-3D extras in 1.2.0: shading by a light, camera moves (pan and push, keyframed) with parallax by depth, the box maker, and a perspective grid guide.
- Free four-corner distort stays with Ctrl+T: under a fixed camera, four freely placed corners usually aren't a true rectangle in 3D.
- Rotation is spin, then tilt, then turn, three angles that aren't wrapped (720° is two whole turns), interpolated with the 1.1 easings. Curved motion paths still bend x and y.
- x and y stay where the pivot shows on the canvas; depth makes a piece smaller without moving that spot. 1.1 pieces are the case depth = tilt = turn = 0 and look exactly as before.
- On a layer, pieces are drawn back to front by depth (ties keep their list order). Pieces that cut through each other show one in front, without the line where they cross.
- The camera moves pieces only: a layer's own pixels stay fixed to the frame (like a foreground). Pieces at depth 0 follow a pan fully, further ones less.
- WebGL2 draws the layers that have 3D, repeating or shaded pieces; layers with only flat pieces keep the 1.1 Canvas 2D path. The CPU path (flatten, merge, colour picker, magic wand, thumbnails, still export) matches the screen within a small tolerance.
- 3D is Full mode only, like animation. The Perspective plane tool's shortcut comes from the free letters (D, M, X).
- Left out of 1.2.0: matching a photo's perspective (fitting the camera to four corners), curved sheets (cylinders, page curl), thickness and extrusion, real shadows, depth of field, the line where pieces cross, distance fade, pieces that always face the camera, 3D on shape layers and text, and frame-by-frame drawing inside a piece.
- Measured before planning: today's CPU perspective warp (`raster/warp.ts`, bilinear, no filtering when it shrinks) takes 24 ms for 1000 × 1000, 102 ms for 2000 × 2000 and 292 ms for 4000 × 3000 on this PC. That's fine for one-off operations and exports, far too slow for the screen, and a big face tilted far back shimmers without mip levels.

### Milestone 7 — Paths, trails and loops, version 1.3.0 (requested after 1.2.0)
Things that travel leave marks. A piece can follow a path drawn on a shape layer and face the way it's going. A path can be drawn on, or eaten away right behind the piece travelling it, like a burning fuse or a route on a map. A piece can leave a trail: smoke, sparks, a comet tail, speed lines. Short cycles repeat by themselves: a layer's drawings (cloth waving in the wind, a flag, a flickering flame) and a piece's keyframes (a swinging sign, a bobbing boat) loop however long the timeline is, and things that never stop turning (wind turbines, waterwheels, fans, gears) spin forever at a steady speed. Started on 2026-11-20, when the user agreed the decisions below for Stop 7A as proposed; they agreed Stop 7B's, 7C's, 7D's and 7E's on 2026-11-21. Agree each later stop's decisions with them as it comes up. Split into five stops; each ends with a working app, `npm run check` green and a report, then waits for "continue". Each item is ticked in the same commit as its work.

Words used in the UI:
- **Follow path:** a piece travels along a path from a shape layer, its **progress** (0–100 %) keyed on the timeline instead of its position.
- **Face direction:** the piece turns to point where it's heading, plus an **angle** for art drawn pointing another way.
- **Trim:** a path shows only from its **Start** to its **End** (each 0–100 % of its length), with an **Offset** that slides both. **Draw on** and **Erase behind** set these up for you.
- **Trail:** what a moving piece leaves behind, from its **emitter point** (a spot on the piece, such as a rocket's nozzle). It is either **Echo** (fading copies of the piece itself) or **Puffs** (stamps of a brush tip that live for a while, growing, drifting and fading, with a colour over their life).
- **Loop drawings:** a frame-by-frame layer's drawings repeat as a **cycle** (A, B, A, B…), or go **back and forth** (A, B, C, B, A…), for the whole timeline.
- **Loop keyframes:** after its last keyframe, a piece starts its moves again from the first (**Loop**) or plays them backwards and forwards (**Back and forth**).
- **Spin forever:** a piece turns about its pivot at a steady **speed** (turns a second, either way), on and on, without keyframes. **Tilt forever** and **Turn forever** do the same in 3D, so a coin can flip or a sign revolve.

Decisions (all agreed, the last for Stop 7E):
- **Trails** (agreed for 7C, with the points below): up to 4 trails a piece, each with its own emitter point and settings, listed in the Trail popover (add, remove, reorder). Puffs are emitted per second and one every so many pixels travelled (either can be 0), and each has a lifetime, size, growth, drift (a speed and direction, such as smoke rising), spread (random scatter), fade and a colour-over-life ramp of 2 to 4 colours, with an option to stretch along the motion (speed lines). An echo is fading copies of the piece a set number of frames apart. Emission (on, off and its rate) is keyed with the usual easings; the colour ramp and other settings are set once. At most 5,000 live puffs a trail. Pictures as puffs are left for later.
- **Deterministic trails:** a trail is worked out from the timeline alone. Each puff's birth, place, size and colour come from the frame and a seed, so scrubbing, playback and exports always show the same smoke, and no simulation state is saved. Puffs are emitted by distance travelled as well as by time, so a fast piece still leaves an unbroken trail.
- **Trail art:** puffs use any brush tip from the library (built-in or the user's own). An echo uses the piece's own pixels.
- **Where trails draw:** on the piece's layer, behind the piece (or in front, as an option). In 3D, puffs face the camera at the emitter's depth, so they shrink with distance.
- **Keyed emission:** emission is keyed on and off, with its rate, so smoke can start at ignition and stop at burn-out. A trail on a piece that doesn't move, given drift, makes a chimney or a candle.
- **Keyed shape paths:** a path on a shape layer can follow, or be followed by, a piece on the timeline. In 1.3.0 a shape object gains keyframes for its trim only (Start, End, Offset), so its row shows in the timeline. Animating a shape's points, style or size is left for later.
- **Trim** (agreed for 7B):
  - It cuts the outline only; the fill stays whole (turn the fill off to draw a whole shape on).
  - A shape with several outlines is trimmed across all of them in turn, as one long line. Offset wraps round a shape whose outlines are all closed, and stops at the ends of an open one.
  - Dashes stay put on the path as the ends move, so a dotted line vanishes dot by dot instead of crawling. Arrowheads sit at the ends that show, pointing along the path there.
  - A shape gets a timeline row under its layer once its trim is keyed (untrimmed shapes get none). **Draw on** (End 0 → 100 %) and **Erase behind** (Start 0 → 100 %) key it from the frame shown over a span you choose (to the timeline's end unless you say otherwise), with an easing.
  - A path a piece follows can tie its Start (erase behind the piece) or End (draw up to it) to that piece, with a gap in pixels along the path; while tied, that end follows the piece instead of its keys.
  - SVG export writes a trimmed shape as it shows at the frame on screen.
- **Following a path:** the piece keeps a link to the path, so editing the path changes the motion. If the path is deleted, the piece keeps the motion it had, baked into keyframes. Following ignores the piece's own x and y keys: a keyed **progress** places it instead, by distance along the path. Any shape's outline can be followed. Only a piece that follows no other piece can follow a path (the top of a tree can, carrying the tree); a curved motion path can also be turned into a shape path (**Motion path to shape**) to style or trim it.
- **Face direction** uses the direction on the canvas, smoothed so a stop or a sharp corner doesn't flick the piece round. It adds to the piece's spin.
- **Loops** (agreed for 7D):
  - A loop is a setting on the layer or piece, not copies, so changing drawing A changes every repeat of it: painting on a repeat paints that drawing everywhere it shows.
  - A frame-by-frame layer's Loop is Off, Cycle or Back and forth (A B C B A B C…, the ends not doubled). The last drawing's end starts as long as the drawing before it.
  - A piece's Loop is Off, Loop or Back and forth. Loop jumps from the last key back to the first, so a seamless loop needs them alike (or Back and forth). Everything keyed loops with it: position, spin, 3D, scroll, fold, progress along a path, and its trails' emission.
  - A looping layer's cycle runs from its first drawing's start to the end of its last drawing. The last drawing gets an end you drag in the timeline, since nothing follows it.
  - A looping piece repeats the span from its first keyframe to its last. Before the first keyframe it holds, as now.
  - The timeline shows the repeats faded beyond the cycle, and onion skin and exports follow them.
  - The picture's own playback mode (Loop, Once, Back and forth) still applies to the whole timeline on top of these.
- **Spin forever** (agreed for 7D):
  - It's a setting of its own on the piece: a speed for spin (and tilt and turn in 3D), in turns a second either way, with its own speed keys (not the piece's keyframes) in a row of their own in the timeline, so keying the speed never keys the position. The extra turn at a frame is the speed added up over time from the first frame. A looping piece's speeds loop too, and the turn keeps adding up.
  - It adds to whatever the keyframes say, so a turbine's blades can turn while its tower is moved or pushed back in 3D, and a hinged waterwheel turns with its group.
  - The speed can be keyed with the usual easings, so a turbine can start up or slow to a stop. The angle at any frame is worked out from all the speeds up to it, so a change in speed never jumps.
  - **Fit to the timeline** rounds the speed to a whole number of turns over the timeline's length, so a looping GIF is seamless (like Loop the scroll).
  - It never changes the keyframes. Turning it off puts the piece back as its keys have it.
- **Save format:** projects hold all of this in `.pigm` version 4, written only when a picture uses something new in 1.3.0, otherwise version 3, 2 or 1 as now.
- **Left out of 1.3.0:** physics (gravity, bouncing, collisions), emitters that aren't on a piece, wind fields, motion blur, and trails on frame-by-frame drawings.
- **Polish and release** (agreed for 7E):
  - A trail's emitter point is set by keyboard with **Emitter X** and **Emitter Y** fields in the Trail popover (in the piece's own pixels; arrows step 1 px, Shift 10), beside dragging its ring on the canvas. The ring itself doesn't take keyboard focus.
  - A looping layer's cycle end, the handle after its last drawing in the timeline, takes keyboard focus; Left and Right move it a frame.
  - The performance budgets stand as written: where one isn't met, optimise until it is, or report the numbers.
  - The README gets a new screenshot of a rocket leaving smoke along a path. The CHANGELOG's "Left out" list is the one above. Version 1.3.0, the installer rebuilt and smoke-tested, and the user is asked before tagging `v1.3.0` (unsigned, as before).

### Milestone 8 — Pigmento for AI assistants (MCP), version 1.4.0 (requested after 1.3.1)
An AI assistant can use Pigmento the way a person does, through the Model Context Protocol (MCP): it looks at the picture, then draws, edits, animates and exports, in the window you have open, while you watch. Each thing it does is one undo step with its own name, so you can step back through its work. It works with any MCP client (Claude Desktop, Claude Code, VS Code, Cursor and others). It's very free by default, and a Settings tab narrows what assistants may do. Split into four stops; each ends with a working app, `npm run check` green and a report, then waits for "continue". Each item is ticked in the same commit as its work.

Words used in the UI:
- **AI assistant:** a program connected to Pigmento over MCP (the window says which one, by the name it gives).
- **Assistant activity:** the side panel listing what assistants have done, newest first, each with its undo step.
- **Stop assistants:** pauses every connected assistant at once; what they ask to do next is refused until you let them go on.

Decisions (agreed with the user on 2026-11-22, Stop 8A's the same day; the rest proposed, to agree at their stop):
- **Any MCP client** (agreed): the standard transports, so no client needs anything made for Pigmento. Over stdio, a client starts `Pigmento.exe --mcp`; over Streamable HTTP, it connects to a local address.
- **In your window, while you watch** (agreed): an assistant works on the picture in the Pigmento window you're using (or another open one it names), never a hidden copy. What it draws appears as it's made.
- **Very free by default, configurable** (agreed): out of the box an assistant can do everything a person can, files included, without asking each time. Settings → AI assistants turns each kind of thing off, or makes it ask.
- **The bridge** (agreed for 8A): `Pigmento.exe --mcp` runs before the one-window-app check and opens no window. It passes messages between the client (stdio) and the Pigmento that's running, over a named pipe only your Windows account can open, starting Pigmento first if it isn't running. Several clients can be connected at once.
- **Streamable HTTP** (agreed for 8A): off by default; when on, it listens on 127.0.0.1 only, on a port you choose, with a token in the address the settings show, and refuses requests from web pages (their Origin) so a website can't reach it.
- **Permissions** (agreed for 8A), each one Allowed, Ask each time or Not allowed, defaults in brackets: look at pictures (allowed); draw and edit (allowed); open, save and export files (allowed, anywhere; optionally only inside one folder); new, close and switch pictures (allowed); change Pigmento's settings (allowed). An assistant can never change the AI assistants settings themselves. "Ask each time" asks in Pigmento's own dialog, naming the assistant and what it wants to do.
- **Watching** (agreed for 8A): strokes and shapes are drawn at a pace you can follow (a stroke over about half a second), or instantly (a setting). The title bar shows a badge while an assistant is connected; clicking it opens Assistant activity. **Stop assistants** is on the badge and the panel, with a keyboard shortcut. Undo labels read "Assistant: …".
- **Seeing the picture** (agreed for 8A): an assistant can ask for the picture, a layer, a region or an animation frame as a PNG, scaled to at most 2048 px on its long side by default, so it can check its own work.
- **Stop 8B** (agreed 2026-11-22, "Yes, as proposed"): about 24 tools, each one thing a person does (pictures and files, layers and selections, painting, the image, effects, `run_action` and `change_settings`). Strokes, lines and paths play out over about half a second (up to 1.5 s); shapes grow as if dragged; fills and effects appear at once. A tool that names a layer makes it the active one; painting stays inside the selection. New and Open use this window unless its picture has unsaved changes, otherwise a new window. **Unsaved changes:** the assistant decides (`unsaved: 'save' | 'discard'`, required when there are some); nothing asks the user. **Existing files** are replaced only with `overwrite: true` (saving to the picture's own file is plain Save). **The user's tools:** an assistant names its brush, size and colour in each call, and the user's tool, brush settings and colours stay as they are (`set_colors` changes them on purpose).
- **Stop 8C** (agreed 2026-11-22, "Yes, as proposed"): eight animation tools, so Pigmento offers exactly 40 (Cursor has long sent only the first 40 tools to its agent): `make_piece` (from the selection, a layer, an image file, or a 3D box), `set_keyframe` (any value at a frame, easing, curve handles, or remove), `set_piece` (name, loop, follow or hinge to a piece, a path and facing its way, spin, back, shade, tiling, pivot, delete), `set_trail`, `set_trim`, `set_animation` (length, frame rate, how it plays, the frame shown, play and stop, the camera and the light), `edit_drawing` and `export_animation`. **The frame shown:** working at a frame goes to it and shows the timeline, as a person would.
- **Left out of 1.4.0** (proposed): access from other computers, Pigmento calling AI models itself (no chat inside Pigmento), recording your own actions as macros, and MCP's sampling and elicitation (Pigmento asks you itself, in its own dialogs).

  - `Pigmento.exe --mcp` runs inside the app, because the packaged app's fuses stop Electron from running as plain Node. It runs before the one-window check.
